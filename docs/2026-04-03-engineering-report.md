## 一、检查工作

今天先对项目做了一轮问题检查，重点覆盖：

- 前端构建可用性
- 后端测试可用性
- 后端鉴权边界
- 健康检查语义
- 前后端真实联调状态
- 假成功接口风险

检查结果已单独输出到：

- [项目当前问题检查报告](./current-issues-report.md)

## 二、识别出的核心问题类型

### 1. 鉴权与权限边界问题

- 调试请求头默认开放
- Bearer Token 校验过于宽松
- 脚手架登录缺少有效密码校验

### 2. 接口语义问题

- 多个写接口在未落库时仍返回成功
- 健康检查更像“配置检查”，不是“服务可达性检查”

### 3. 前端联调问题

- 前端大量页面数据来自本地静态常量
- 已定义的 API 调用未真正覆盖主要页面链路

## 三、已完成的修复

### A. 后端安全修复

- 调整鉴权配置默认值，关闭调试请求头的默认开放
- 为脚手架 token 增加签名与解析逻辑
- 无效 Bearer Token 不再默认提升为已登录用户
- 脚手架登录改为必须校验密码

### B. 后端接口修复

- 将未真正实现的写接口改为明确返回 `501 Not Implemented`
- 保留只读接口与已有数据库逻辑，不再给未落库能力返回假成功

### C. 健康检查修复

- 从“是否有配置对象”改为“是否已配置 + 是否实际可达”的双层信息
- 为 PostgreSQL、Redis、RabbitMQ、Meilisearch 增加探测能力

### D. 前端联调修复

- 前端重新接入健康检查、文章、论坛、空间资料、站点内容接口
- 空间页重新接入登录与 `/users/me`
- 首页和分页面在保留当前视觉结构的前提下恢复真实数据来源
