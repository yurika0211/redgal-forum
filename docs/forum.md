# 00 背景介绍

![](https://p.sda1.dev/31/b878157e39c0003105e7860e321e93f8/image.png)

“该建redgal论坛了”

Q：“你看你蛆得，还有人样吗？这论坛拿来干什么呢，感觉是`galgame`论坛的话，那背后肯定全是些违禁的内容啊，不怕帽子叔叔把你请去喝茶？”

A：“啥意思呢，我做这个论坛的想法肯定是让大家自己发表一些自己的游戏感悟，类似于观后感一样的东西，你怎么能说是违禁的内容啊，现在我的主要想法是建造一个只有本校同学才能注册登陆的网站，当然，网站本身也需要面向外界做展示，这样一想功能还挺复杂的，所以基本思路就是：这个网站有两面，一面是面向未登陆用户的，展示大家想要公之于众的的游戏感想，感想也就是文章，需要做一个公开访问和登陆访问还有私有访问的三层。”

Q：“就这点东西，换个网站不是全都能实现，你建这个论坛还有什么特别之处？”

A：“懂你意思，最大的区分点在于，这个论坛是面向`redgal`本校的成员的，所以这里肯定还有一个公开的论坛区，大家可以自由发帖，然后集中讨论和分享一些有趣的事物，相对于群聊，这样可以持久化的形式对于群聊发展更有价值。这里根据情况，会考虑设置匿名讨论版这样的东西，最重要的一点，也就是最有价值的一点，可以设置一个展示墙，用来记录一级级群友的社团生活，那些藏在流逝时光当总的热泪与感动，值得被珍藏，然后随着被时光酿造得愈发醇香。”

Q：“那作为一个已注册，且登陆的群友，我可以干什么呢？”

A：“本校群友可以拥有个人的页面，可以修改自己的昵称、签名、个人介绍、头像，然后可以管理自己发表的文章，可以在收藏、已玩、想玩、搁置、抛弃的作品等栏目当中，导入`bangumi`的数据。刚才那是针对个人的，已经注册登陆的用户可以参与发帖讨论，也可以参与匿名版的讨论，对于展示墙的内容，一般用户如果想要上传的话，需要经过管理员审批，理论上论坛是不允许黄暴内容的出现的，所以需要大家注意一下。”

# 01 技术选型：构建一个能支撑1000人同时在线的网站

## 1.1 前端：React+TypeScript

![](https://p.sda1.dev/31/767a7e011d6703d0f4f80537dbaf5545/image.png)


1. **复杂状态与权限细分的需求（TypeScript 的必要性）**  
你的场景中提到了非常细腻的三层访问控制（公开、登录、私有）以及多种内容状态（想玩、已玩、搁置等）。  
数据模型严谨化： 在处理来自 Bangumi 的外部导入数据时，数据结构往往非常复杂。使用 TypeScript 可以定义严格的 Interface（接口），确保在展示“已玩”或“收藏”列表时，不会因为后端字段缺失或类型错误导致页面崩溃。  
权限逻辑的安全感： “三层访问”意味着前端需要根据用户身份动态渲染内容。TS 的静态类型检查能确保你在编写路由守卫或内容过滤器时，逻辑覆盖到所有用户角色，减少因逻辑疏忽导致“私有感悟”被公开泄露的风险。

2. **高度组件化的互动界面（React 的优势)**  
论坛的核心是“信息流”和“互动”，而你的项目还有“展示墙”和“个人主页”等特殊模块。  
展示墙（Memories Wall）： 这种充满“热泪与感动”的模块通常需要精细的交互逻辑和动画效果。React 的声明式 UI 让你只需关注“数据是什么样，界面就长什么样”，配合成熟的动画库（如 Framer Motion），能轻松实现情感化设计的落地。  
功能复用： 比如“文章卡片”组件，它可能同时出现在“公开感悟区”、“个人管理页”和“搜索结果页”中。React 的组件化开发能让你实现“一次编写，到处运行”，极大提升单人或小团队的开发效率。

3. **第三方数据集成（Bangumi 导入）**  
异步逻辑处理： 导入 Bangumi 数据涉及跨域请求、数据清洗和同步。React 的 Hooks（如 useEffect, useMemo）结合 TS 的类型定义，可以让这些异步数据流变得清晰可控。  
中间层建模： 你可以利用 TS 为 Bangumi API 的返回结果建立中间层模型，将外部不规范的数据转化为论坛内部标准的 GameSubject 类型，降低业务逻辑与外部接口的耦合。

4. **“持久化”与“匿名版”的工程化挑战**  
匿名机制的实现： 匿名讨论版通常需要在前端屏蔽真实 ID 或生成临时马甲。React 的状态管理（如 Zustand 或 Redux）能确保匿名状态在页面切换时依然保持一致且逻辑隔离。  
长效维护性（给下一届的礼物）： 你提到这是“本校成员”的论坛，希望能记录“一级级群友的社团生活”。这意味着项目需要长期运行和交接。  
TypeScript 即文档： 即使一年后你毕业了，新加入的社长看到定义良好的 Article.ts 和 UserRole.ts，也能迅速理解业务逻辑，不至于让论坛变成无人能修的“烂尾楼”。

5. **规避“喝茶”风险的审核流前端实现**  
管理员审批工作台： 针对“展示墙”内容的上传，你需要一个高效的后台审核界面。React 的成熟生态（如 Ant Design 或 Arco Design）提供了大量的表格和表单组件，让你能以极低的成本开发出一套流畅的审核系统，确保“黄暴内容”在前端就被有效拦截。


## 1.2 后端：Golang+gin框架+Redis+RabbitMQ+Meilisearch

![](https://p.sda1.dev/31/9dbd0279f39ce6be0a65421f4b18f54c/image.png)

![](https://p.sda1.dev/31/3587b82a4747c1481a0d1639531066c9/image.png)

![](https://p.sda1.dev/31/15bfd47bb2425ea1d5160301dbae429f/image.png)

![](https://p.sda1.dev/31/8e0829d69fc821425c2bacc6e4e9758f/image.png)

>为了兼顾服务器成本和应对突发并发的需求（S），我们的目标是打造一个轻量、高性能且安全的后端（T）。为此，我们采用了 Golang + Gin 的核心架构，利用其极低的内存占用和优秀的中间件机制实现了严密的权限管控与敏感词拦截；同时引入 Redis 应对高频浏览和接口防刷，并用 RabbitMQ 将诸如‘Bangumi 数据导入’这类耗时任务异步化（A）。这套组合拳最终（R）让我们不仅在有限的服务器资源上榨干了性能，还保证了用户体验的绝对流畅，并为社团未来的长期安全运营打下了坚实基础。

1. S - Situation (情境 / 背景)  
结合校园社团项目的实际限制与业务特征。  
服务器资源受限： 作为社团或个人的开源项目，通常只能部署在配置有限的云服务器（如 2核4G 的轻量应用服务器）上，预算吃紧，对内存和 CPU 的占用要求极度苛刻。  
业务场景多样： 涉及三层复杂的鉴权（公开、登录、私有）、高频的读操作（公开文章和展示墙）、耗时的第三方网络请求（Bangumi 数据同步），以及敏感的内容风控审核。  
流量波峰明显： 校园论坛平时流量平稳，但在迎新季、某款现象级游戏发售、或匿名版爆发吃瓜事件时，可能会出现突发的并发访问。  
2. T - Task (任务 / 目标)
基于上述背景，后端架构需要达成什么目标。

>核心目标： 
在有限的服务器资源下，构建一个高并发、低延迟、高可用的后端服务。
具体指标： 最大限度压榨服务器性能，降低运行成本、实现严密的路由鉴权与接口防刷机制（保护系统不崩溃，不被发垃圾贴）、优雅处理耗时任务（如批量拉取第三方数据），保证主干流程的响应速度。

3. A - Action (行动 / 选型方案与理由)
详细拆解这套技术栈是如何完美解决上述任务的。  
**Golang (核心语言)：低耗高效的“性能怪兽”**  
极低资源占用： 编译型语言，无需像 Java 那样启动笨重的 JVM 虚拟机。极低的内存占用非常适合学生党配置不高的服务器。  
原生高并发支持： 借助 Goroutine，可以用极小的开销处理大量并发请求，轻松应对匿名版的集中讨论。  
易于部署与交接： Go 编译后直接生成一个独立的可执行文件，丢到服务器上就能跑，没有任何环境依赖。这对于以后把项目交接给下一届学弟学妹来说，简直是福音。  
**Gin (Web 框架)：轻量、极速与中间件利器**  
极致的路由性能： Gin 是 Go 生态中最快、最流行的轻量级框架之一。  
优雅的中间件机制（解决三层访问与风控）： 论坛的三层权限控制（游客/登录/私有），可以通过编写 Gin 的 Auth 中间件轻松实现拦截。同时，针对你担心的“喝茶”风险，可以写一个敏感词过滤的中间件，在接口层直接阻断违规词汇的提交。  
**Redis (缓存层)：速度与状态管理的“万金油”**  
高频读取加速： “展示墙”和“公开讨论区”这类读多写少的数据，直接扔进 Redis 缓存，大幅减轻数据库压力，做到页面秒开。  
接口防刷与限流： 匿名版极易遭到恶意灌水。利用 Redis 可以轻松实现 Rate Limiting（例如：限制同一个 IP 或马甲每分钟只能发 3 帖），保障论坛环境。
Token 管理： 用于存储用户登录状态和身份令牌，实现快速的鉴权验证。    
**RabbitMQ (消息队列)：异步解耦的“缓冲带”**     
异步处理耗时任务： 当群友点击“导入 Bangumi 数据”时，如果是同步操作，页面会一直转圈卡顿甚至超时。引入 MQ 后，后端只需把这个任务扔进队列，立刻返回“导入中”给前端。后台的消费者（Consumer）再慢慢去调用 Bangumi API 抓取数据，极大地提升了用户体验。  
业务解耦： 当普通用户在“展示墙”提交内容时，系统将审核任务发到 MQ，通知管理员去后台审核。这种解耦让核心发帖流程更加轻量。

4. **R - Result (结果 / 收益)**
架构落地的预期成效。  
降本增效： 以极低的服务器成本（甚至是几十块钱的学生机）支撑起了完整的社团生态，且页面响应速度极快。  
极致体验： 通过引入 Redis 缓存和 RabbitMQ 异步队列，用户在浏览展示墙、导入长篇游戏记录时如丝般顺滑，不会遇到卡顿和请求超时。  
安全可控： 借助 Gin 中间件的严格鉴权、Redis 的限流防刷，配合管理员的审核流，最大程度规避了黄暴内容风险，确保论坛健康、持久地运行。

## 1.3 数据库：PostgresSQL

![](https://p.sda1.dev/31/4674eee6a3fd715ba6396f70f8527c96/image.png)

>考虑到咱们论坛数据关系极其复杂，且需要接入 Bangumi 的非标准外部数据，同时还要保证这些‘社团回忆’的绝对安全（S），我们需要一个既严谨又灵活的底层存储方案（T）。因此，我排除了普通的方案，坚决选用了 PostgreSQL（A）。除了它工业级的稳定性和 ACID 合规性外，最打动我的是它原生的 JSONB 和数组类型支持，这让我们能以极低的成本无缝整合 Bangumi 的游戏数据，且不失查询性能。最终（R），PG 为整个系统提供了一个极其健壮、免维护且极具扩展性的数据底座，完美兜住了所有的复杂业务逻辑。

1. S - Situation (情境 / 背景)  
描述论坛在数据存储层面面临的特殊业务环境和痛点。  
数据关系错综复杂： 论坛不仅有常规的“用户-文章-评论”关系，还有“三层可见度权限”、“多维度的游戏状态（想玩/已玩/搁置）”以及复杂的匿名版互动逻辑。  
异构数据的接入： 需要对接 Bangumi 获取游戏元数据，这类第三方接口返回的往往是层级深、字段多且容易变动的嵌套 JSON 数据。如果用传统的表结构去一一映射，建表和维护的过程将是一场灾难。  
数据资产的珍贵性： 论坛的定位是“持久化留存群友的社团生活”，展示墙和个人的游戏感悟是核心资产，绝对不能容忍数据丢失、错乱或因为历史遗留问题导致“坏数据”。  

2. T - Task (任务 / 目标)  
基于上述背景，你需要一个什么样的数据库来兜底。  
核心目标： 选型一个极其稳健、支持复杂关系查询，且能灵活兼容半结构化数据（JSON）的开源关系型数据库。  
具体指标：保证绝对的数据一致性和完整性（ACID）、以最低的开发成本优雅地存储和查询外部导入的 API 数据、支持高效的复杂查询（如多表联查、树状评论检索），为后期的功能迭代留足空间。

3. A - Action (行动 / 选型方案与理由)
详细阐述为什么在众多数据库（如 MySQL、MongoDB）中，最终拍板了 PostgreSQL。  
**极度严谨的“数据守门员”（优于 MySQL）：**   
PG 以极强的数据完整性和严格的约束著称。它不会像某些旧版数据库那样对超长字符串进行“静默截断”，也不会容忍类型模糊。配合后端的 Golang 和前端的 TypeScript，从头到尾打造了坚不可摧的全链路类型安全，确保“回忆”被毫发无损地保存。  
**杀手锏：强大的 JSONB 支持（完美契合 Bangumi 导入）：**  
面对 Bangumi 庞大且灵活的游戏条目信息，PG 原生支持 JSONB 数据类型。你可以直接将第三方 API 返回的复杂游戏信息作为一个 JSONB 字段存入数据库中，并且可以直接对 JSON 内部的属性进行高效的索引和查询（例如：直接查询 JSONB 中 tags 包含“Galgame”的记录）。这完美融合了关系型数据库的严谨和 NoSQL（如 MongoDB）的灵活。  
**原生数组类型（Array Types）简化表结构：**  
论坛中大量的“标签（Tags）”、“图片画廊（展示墙的图集）”等功能，如果用传统方式需要建立多张关联表。在 PG 中，可以直接使用数组类型存储这些字符串或链接，大幅精简了数据库架构（Schema），让后端的 CRUD 逻辑清爽无比。   
**强大的高级查询能力：**  
面对匿名版可能出现的“楼中楼”树状回复，PG 的 CTE（公共表表达式/递归查询）能够以极高的性能一次性拉取整个讨论树，不需要在业务层写丑陋的循环查询。

4. **R - Result (结果 / 收益)**  
使用 PostgreSQL 给项目带来的实际价值。  
**开发效能飙升**： 借助 JSONB 和原生数组，免去了为第三方数据建立几十张关联表的折磨，数据建模时间缩短了 XX%。  
**坚如磐石的稳定性**： 论坛上线后，面对复杂的并发评论和权限判定，PG 依靠其强大的事务机制保证了零脏数据产生，保障了社团数字资产的绝对安全。  
**面向未来的扩展性**： 无论是未来想要增加全文搜索功能（PG 原生支持不错的全文检索），还是引入更复杂的社交关系图谱，PG 丰富的插件生态和高级特性都能轻松应对，无需中途更换数据库。



# 02 需求分析

## 2.1 通用功能

### 2.1.1注册登陆

注册登陆这一块我觉得需要限制本校的加入，那就需要想一个比较好的手段，一个是川大本身的邮箱，使用川大的邮箱，然后有川大邮箱的人邀请，并且网站管理员进行审核，非本校一旦被发现将封禁帐号。为了避免有人来保护，所以需要对网站各方面都进行防护，比如使用`Cloud Flare`的盾。

注册的用户名要求，用户名可以搞得高级一点，支持多种语言，甚至可以加注释，在论坛增加等级制度，做一些事情就可以增加一些经验

## 2.2 用户层

### 2.2.1 用户分级

#### 2.2.1.1 未认证用户

这个几乎没有操作权限，和一般的游客没有区别，只能参与基础的接龙。

#### 2.2.1.2 认证普通用户

这个拥有大部分用户权限，可以有个人空间，参与讨论，发表文章，投稿

#### 2.2.1.3 管理员

拥有大部分网站权限，包括对用户的状态进行修改，发起接龙等，发起征文等。还拥有删帖和删文章等高级权限。可以审批用户的认证状态，但是一个用户是否通过认证，需要至少三个管理员的认证，或者超级管理员直接认证，不然不能通过。

#### 2.2.1.4 超级管理员

掌握网站的所有权限，拥有独立的`dashboard`，拥有整个网站的生杀大权

### 2.2.1 用户个人主页

#### 2.2.1.1 基本信息

用户头像、个性签名、用户名称

#### 2.2.1.2 社交帐号

自己一些别的社交平台的展示

#### 2.2.1.3 个人动态展示

类似与推特的模式

#### 2.2.1.4 个人游玩作品的标记（支持bangumi一键导入和搜索）

做成bangumi的模式

## 2.3 论坛特色功能

### 2.3.1 讨论版

这个可以做成匿名聊天室的功能，大家可以在聊天室公开聊，也可以私聊。

### 2.3.2 展示墙

这个用来存放十二川器之类的东西，还有大家一起跨年闪闪发光的回忆。

### 2.3.3 ChatBot（Luckybot）

这个我还在写，现在的想法是基于`nano bot`做一些拓展，到时候大部分人的页面应该只能对话，超级管理员可以进行更高的操作。

### 2.3.4 收集表功能

可以让大家脱离qq的接龙，拥抱更加遍历和持久化的方式。

### 2.3.5 征文功能

支持各种形式的文章上传，甚至是站内的文章转发
